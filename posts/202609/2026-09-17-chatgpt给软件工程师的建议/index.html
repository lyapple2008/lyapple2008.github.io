AI Coding 已经进入软件开发的完整流程：读代码、写代码、补测试、查问题、改文档，甚至可以自己运行命令，再根据结果继续迭代。它带来的不只是效率提升，也有一个越来越难回避的问题：

当 AI 可以完成越来越多开发工作，以后还需要软件工程师吗？如果需要，工程师真正值钱的能力又是什么？

最近我把这个问题抛给了 ChatGPT，又结合自己的情况继续追问：一个已经做了多年 C/C++、音视频和移动端开发的工程师，应该继续深挖原来的技术栈，还是转向 AI Agent？如果要转，具体该学什么？

讨论很长，下面不是聊天记录的原样搬运，而是我重新整理后的结论和行动路线。

先说答案：软件工程师仍然需要，但“会写代码”不再足以定义一个软件工程师。

AI 改变的不是软件是否还要有人负责，而是代码正在从稀缺的生产能力，变成越来越便宜的生产资料。未来更稀缺的，是能把模糊问题变成正确系统、能驾驭 AI 完成交付，并能判断结果是否可靠的人。

一、消失的不是工程师，而是代码生产的溢价#

过去的软件开发流程大致是：

1

需求 → 设计 → 写代码 → Debug → 测试 → 发布 → 维护

其中大量时间花在查 API、写样板代码、补测试、重构和整理文档上。如今这些环节正在被 AI 快速压缩，新的流程更像：

1
2

问题 → 需求澄清 → 系统设计 → 任务拆解 → Agent 实现
     → 自动验证 → 人工决策 → 上线 → 持续反馈

这里有一个很重要的变化：代码生产的成本下降了，决策、验证和责任的成本却没有一起消失。

AI 可以在几分钟内生成上千行代码，但它并不知道业务到底想解决什么，不会天然理解系统里的隐性约束，也不会替团队承担线上事故的责任。生成得越快，人越需要回答三个问题：

  1. 做的是不是正确的问题？
  2. 采用的是不是合适的系统方案？
  3. 结果凭什么值得相信？

这意味着软件开发正在经历一次“抽象层上移”。过去工程师的主要产出是代码，接下来更重要的产出会逐渐变成：清晰的问题定义、可执行的规格、合理的系统边界，以及可验证的交付结果。

二、未来更重要的五种能力#

把工程师的能力从底到顶排列，大致可以分成五层：

1
2
3
4
5

问题与产品判断       最稀缺
系统设计与工程取舍
领域知识与工程经验
验证、测试与可观测性
编码与工具使用       逐渐普及

这不是说 Coding 不再重要，而是 Coding 的角色变了：它正在从主要产出，变成理解系统、约束 AI 和处理疑难问题的基础能力。

1. 定义问题，而不是急着写代码#

假设需求只有一句话：“做一个 AI 实时字幕功能。”

接到需求就开始选 Whisper、接音频、写界面，当然可以很快看到 Demo。但真正决定这个功能能不能落地的，是更前面的那些问题：

  • 音频来自麦克风、系统播放，还是直播链路？
  • 可接受延迟是 200 毫秒、1 秒还是 3 秒？
  • 音频是否允许上传云端？断网时怎么处理？
  • 支持哪些语言，翻译按流式输出还是按句提交？
  • 字幕“稳定”的定义是什么，已经展示的文字是否允许回改？
  • 目标设备、功耗和内存上限是多少？
  • 系统 API 是否真的允许采集目标音频？

这些问题没有答案，再强的模型也只会更快地做出错误的东西。

所以未来第一项核心能力不是 Prompt 技巧，而是 Problem Framing：识别真实目标，发现约束，把模糊需求拆成可以验证的问题。AI 擅长在边界内求解，人必须先画出正确的边界。

2. 设计系统，而不只是拼接模块#

AI 很擅长生成函数、类、接口和局部测试，却不天然擅长为一个长期演进的系统负责。一个真实系统仍然需要工程师决定：

  • 数据从哪里来，由谁拥有；
  • 状态放在哪里，生命周期如何结束；
  • 哪些步骤同步，哪些步骤异步；
  • 线程如何协作，错误如何传播；
  • 性能瓶颈可能出现在哪里；
  • 如何升级、降级、回滚和观测。

还是以实时字幕为例，链路可以画成：

1

Audio Capture → PCM → VAD → ASR → 稳定化 → 翻译 → 字幕展示

AI 可以分别实现每个模块，但“为什么这样拆”仍是人的工作。哪里需要 streaming，谁管理 buffer 的 ownership，ASR 的中间结果何时 commit，翻译失败是否阻塞原文字幕——这些选择共同决定了系统是否可用。

3. 保留真正的领域深度#

当通用代码越来越容易生成，领域知识反而会更有价值。

“会写 Python”很容易被模型复制；但理解 AEC、NS、AGC、VAD、重采样、SIMD、缓存、实时线程、延迟和功耗之间的关系，就不是生成一段代码那么简单。这里面包含长期积累的边界条件、失败经验和取舍能力。

这也是我不打算丢掉音视频和 C/C++，完全转成“Agent 开发者”的原因。更合理的组合是：

AI 应该放大已有的专业能力，而不是把它替换成一套很快就会普及的工具操作。

4. 建立验证 AI 的能力#

AI 生成的代码量越大，工程师越不能只靠“看起来没问题”来验收。未来很常见的工作流会是：

1

Human → Spec → Agent → 大量代码 → 自动验证 → Human Review

真正困难的问题是：怎么证明 Agent 写对了？

因此下面这些传统工程能力不但不会过时，反而会成为 AI Coding 的基础设施：

  • 单元测试、集成测试、端到端测试和回归测试；
  • 延迟、吞吐、CPU、内存、功耗和准确率 Benchmark；
  • 日志、指标、Trace、Profiling 和 Crash 分析；
  • 静态分析、Sanitizer、Fuzzing、断言和类型系统。

我最近研究的 gtest、ASAN、UBSAN、TSAN 和 simpleperf，看起来都不是最热门的“AI 技术”，却恰好是在给 AI 产出建立护栏。代码可以由 Agent 写，验收标准不能临时猜。

人的工作会越来越接近 Architect、Reviewer 和 Agent Operator 的组合：给出上下文和约束，拆分任务，选择工具，处理冲突，并对最终结果负责。

但这不意味着可以放弃 Coding。不会 C++ 的人，很难发现一个看似普通的 std::vector<float> 背后是否存在多余分配、拷贝、生命周期、对齐或缓存问题；不了解并发的人，也很难识别 AI 写出的偶发竞态。不一定要亲手写完每一行，但必须有能力判断这些代码是否可信。

三、哪些岗位会减少，哪些工程师会更值钱#

软件工程岗位总量是否一定减少，很难准确预测；但岗位结构发生变化几乎是确定的。

简单 CRUD、普通页面、常规 API、一次性脚本和数据转换，这些边界清楚、容易验证的工作会最先被压缩。不是它们完全不再需要人，而是完成同样工作需要的人会更少。

操作系统、编译器、数据库、音视频、网络、安全、机器人、嵌入式、高性能计算和大型分布式系统，则不会因为代码生成变快就突然变简单。它们面对的是现实世界的复杂约束，需要长期的工程取舍、跨模块理解和故障处理。

未来的软件工程师可能形成三种分化：

类型能力结构处境
纯代码生产者按明确需求实现功能工作最容易被压缩
AI 增强型开发者Coding + AI 工具产出明显提高
AI 增强型领域工程师领域知识 + 系统设计 + Coding + Agent + 验证能解决复杂问题，杠杆最高

我想走的是第三条路。目标不是和 AI 比谁敲代码快，而是把自己的领域经验、工程判断和 AI 的执行能力组合起来，完成过去需要更多人协作才能完成的系统。

这个结论也延续了我之前对 AI Coding 的看法。我曾在《关于 AI Coding 的一些感想和后续规划》里写过，AI 的能力边界很大程度受使用者影响，生产代码的责任仍在人身上。现在再往前一步看，真正的变化不只是“用 AI 写得更快”，而是要围绕 AI 重新设计整套软件工程流程。

四、我的进阶路线：从 AI Coding 到 AI-Native Engineering#

结合我目前的基础，更合适的路线不是从零转行做大模型，也不是追逐所有 Agent 框架，而是：

这条路线可以用 6～9 个月建立基本体系，但各阶段不需要等前一阶段“学完”才开始。更有效的节奏始终是：学一点，马上放进真实项目；遇到问题，再回来补知识。

Stage 0：补强软件工程闭环#

时间：2～4 周。

这一阶段不是重新学习语法，而是把注意力从 Coding 拉回完整交付：

1
2

Requirement → Spec → Architecture → Implementation
            → Test → Benchmark → Release → Observability

重点补三块：

  • Architecture：模块、接口、依赖、ownership、生命周期、状态、并发和错误处理；
  • Testing：单测、集成测试、回归、Benchmark、Fuzzing 和静态分析；
  • Profiling：CPU、内存、I/O、Cache、SIMD、功耗、延迟和吞吐。

核心不是背设计模式，而是能解释为什么系统应该这样拆、为什么这个实现会慢、为什么这个结果值得信任。

Stage 1：形成稳定的 AI Coding 工作流#

时间：3～6 周。

先不急着开发 Agent Framework，而是把 Codex、Claude Code 或 Cursor 用到工程级。对中等以上的任务，固定练习五个步骤：

  1. Explore：只读工程，定位相关代码、调用链和风险；
  2. Plan：输出修改方案、影响范围、验证方式，先不动代码；
  3. Implement：按照确认后的计划分步实现；
  4. Verify：编译、测试、检查 Diff，并补充必要的性能验证；
  5. Review：换一个上下文或 Agent，从正确性、并发、性能、兼容性和回归风险重新审查。

这五步的价值不在于流程看起来完整，而在于把“写代码”放回一个可控制、可复核的闭环里。

Stage 2：学习 Specification 与 SDD#

时间：3～6 周。

AI 很会执行，但人必须先说清楚执行什么。这个阶段要能区分并使用：

  • Requirement；
  • Specification；
  • Design；
  • Task；
  • Acceptance Criteria；
  • Test Case；
  • Architecture Decision。

OpenSpec 一类工具值得学习，但重点不是记命令，而是理解从 Explore、Propose、Review、Apply 到 Archive 的变更过程：设计错了如何修订，什么时候应该更新 Spec，什么时候需要重新 Proposal。

可以把 Specification 看成 AI Coding 的“上游源代码”。它未必像代码一样可以直接执行，却决定了 Agent 最终生成什么，以及人用什么标准验收。

Stage 3：亲手实现一个 Mini Agent#

时间：1～2 个月。

这一阶段才正式学习 Agent、LLM、Tool Calling、Context、Planning、Memory、Reflection 和 Sub-agent。最好的入口不是先读几十个框架，而是用 TypeScript 写一个最小 Agent：

1

User → LLM → Tool Call → Tool Result → LLM → Answer

第一版只需要 filesystem、calculator、shell 三个 Tool；第二版加入多轮上下文和循环执行：

 1
 2
 3
 4
 5

 8

11

while (!done) {
  const response = await llm(messages);

  if (response.toolCall) {
    const result = await execute(response.toolCall);
    messages.push(result);
    continue;
  }

  return response.answer;
}

真正理解这个循环后，再读各种 Agent Framework，就能看见包装之下共同的骨架。

TypeScript 不需要从头学遍，只要先掌握 type、interface、泛型、联合类型、Promise、async/await、模块和 npm，够用就往项目里走。

Stage 4：理解 MCP、工具与安全边界#

时间：约 1 个月。

Agent Loop 本身并不神秘，工程复杂度主要来自 Agent 与真实世界的连接：

1

Agent + Tools + Context + State + Permissions + Reliability + Security

这个阶段要理解 Tool、Resource、Prompt 和 MCP Client 如何连接文件系统、GitHub、数据库和其他服务。除了“能调用”，还要继续追问：

  • 工具权限如何限制；
  • 高风险操作何时需要人工批准；
  • 第三方返回内容是否可信；
  • 执行失败如何重试或回滚；
  • 日志里如何避免泄露敏感信息。

Agent 能操作的东西越多，安全边界就越重要。

Stage 5：阅读真实的 Agent Runtime#

时间：1～2 个月。

有了 Mini Agent 和 MCP 的基础，再研究 Codex、OpenClaw、Pi 或 Agent SDK 这类真实系统。不要从源码第一行顺序读，而是沿着运行链路追踪：

1
2

CLI → Runtime → Session → Agent Loop → LLM
    → Tool → Context → Memory → Sub-agent

面对任何 Agent Runtime，都可以用八个问题拆解：

  1. Agent Loop 在哪里？
  2. Context 在什么时候组装、裁剪和压缩？
  3. Tool 如何注册、选择和执行？
  4. Session、状态和 Checkpoint 如何保存？
  5. 长上下文怎样摘要，信息丢失如何处理？
  6. 执行中断后怎样恢复？
  7. Sub-agent 如何隔离上下文、并行工作和汇总结果？
  8. 权限、审批和审计边界在哪里？

我之前整理过《从 Claude Code 学习 Agent 开发》，当时得到的结论是“一个循环加工具就是 Agent”。这句话适合解释原理；真正到了工程里，难点则是如何让这个循环在长期运行、上下文变化和工具失败时仍然可靠。

Stage 6：建立 AI-Native 开发方式#

这是持续演进的阶段。最终目标不是“会用 Copilot”，而是让整个开发过程围绕人和 Agent 的分工重新组织：

1
2
3

Idea → Explore → Specification → Architecture
     → Implementation Agent → Test Agent → Review Agent
     → Benchmark → Human Approval → Release

人在关键决策点介入，Agent 承担可拆分、可验证的执行工作。任何一步都不能只因为“模型说完成了”就算完成，最终仍要回到构建结果、测试、指标和验收标准。

五、用三个项目把路线串起来#

学习 Agent 最容易掉进的坑，是看了很多框架，收藏了很多名词，却没有一条真实链路把它们连起来。与其做几十个 Demo，不如做三个逐步升级的项目。

Project 1：Mini Agent#

用 TypeScript 实现 LLM、Tool Calling 和 Agent Loop，控制在 1～2 周。目标不是做一个能用的产品，而是把 Agent 的最小原理亲手跑通。

Project 2：Audio Coding Agent#

让 Agent 分析一个真实的 C++ Audio Pipeline，寻找 CPU Hotspot、内存拷贝、重采样开销、线程问题和潜在竞态。给它配置 filesystem、代码搜索、Git、编译、gtest 和 simpleperf 等工具，形成：

1

Analyze → Plan → Modify → Build → Test → Benchmark → Report

这个项目能把我已有的 C++、音频、性能优化经验和 Agent Engineering 串在一起。与通用 Coding Agent 相比，领域知识会真正参与结果判断。

Project 3：AI-Native 实时字幕应用#

最后选择一个完整项目，例如 iOS 双语实时字幕，从想法开始严格走一遍 Spec、架构、任务拆分、实现、测试、Benchmark 和发布流程。可以让不同 Agent 分别承担探索、编码、测试、性能和 Review，但每一步都必须有明确输入、输出和验收标准。

这个项目不是为了证明“一人公司”或“无人开发”已经实现，而是建立一套自己真正用得起来的个人 AI 软件工程体系。

六、时间如何分配#

如果每周可以投入 8～10 小时，我准备按下面的比例推进：

阶段参考时间主要产出
工程闭环补强2～4 周测试、性能与架构检查清单
AI Coding 工作流3～6 周Explore 到 Review 的稳定流程
Specification / SDD3～6 周可执行、可验收的项目 Spec
Agent 原理4～6 周Mini Agent
MCP / Tool3～4 周带权限边界的工具集成
Runtime 研究4～8 周对一个真实 Agent 的源码分析
AI-Native Engineering持续完整项目与复盘

时间不是硬指标。判断一个阶段是否完成的标准，不是“资料看完了”，而是能否拿出可以运行、可以验证、可以复盘的产物。

  • Running Codex safely：理解权限、环境和人工审批；
  • A practical guide to building agents：建立 Agent 的整体模型；
  • TypeScript Handbook 与 Modules：补齐实现 Agent 所需的 TypeScript 子集；
  • OpenSpec Quickstart：把 Spec 驱动流程放进真实项目。

读资料时不追求“系统学完”。每看懂一个概念，就在项目中找到它的位置；没有项目对应的知识，过一段时间大概率还会忘掉。

八、最后：不要成为工具收藏家#

这次讨论最终给我的提醒，不是赶紧转行，也不是赶紧再学一个热门框架，而是重新确认自己的能力组合：

未来优秀的软件工程师，应该能定义问题、设计系统、驾驭 Agent、验证结果，并对最终交付负责。

因此，不应该按照“先学 TypeScript，再学 Agent，再学 MCP，再学某个框架”的课程目录前进。更有效的方式，是始终围绕一个真实项目：项目需要什么，就补什么；做出结果，再复盘哪些判断可以沉淀成 Spec、测试、工具或工作流。

代码正在变便宜，但正确的软件并没有因此自动出现。会写代码仍然重要，只是它不再是终点。接下来真正值得投入的，是把领域经验、系统工程和 AI 组织成一套能持续交付的能力。
